## The opening

> “This project connects patient registration, treatment progress, prescriptions and billing. I will follow one patient through the system to show how those records stay together.”

## The walkthrough

| Time | Show | Explain |
| :--- | :--- | :--- |
| **0:00–0:45** | Sign in and open the dashboard. | The account has a server-side session. The dashboard retrieves its summary counts from MySQL. |
| **0:45–1:45** | Register a fictional patient and note their ID. | Saving the form creates a patient record. The generated ID becomes the reference for the later steps. |
| **1:45–2:45** | Look up that ID in Patient Service and add treatment progress. | Record the completed step, remaining steps and next appointment date. |
| **2:45–3:30** | Switch to Prescription and save a demonstration entry. | A shared patient selection connects this record to the same patient. |
| **3:30–4:15** | Switch to Billing and enter a total and partial payment. | The application calculates the remaining balance and stores the bill. |
| **4:15–5:15** | Open Patient Records and search for the patient. | Show how their details, care and payments appear together. |
| **5:15–6:00** | Open Edit Patient, return to the dashboard, then log out. | Existing records can be loaded for correction; logout ends the session. |

## Explain the system in three layers

1. **Browser:** HTML structures the pages, CSS styles them, and JavaScript handles interactions and API requests.
2. **Server:** Express receives requests, checks login sessions and executes the database operations.
3. **Database:** MySQL persists accounts, patients, treatment, prescriptions, billing and the reminder log.

An example to use: “When I save a patient, the browser sends JSON to Express. Express uses the current session's account ID in the insert. MySQL stores the record and the browser displays the patient ID.”

## Questions you can discuss

<details>
<summary><b>Why use a patient ID?</b></summary>

Names can be similar or change. The application uses a generated ID as the common reference for finding patients and attaching clinical records. Account ownership is tracked separately through `user_id`.

</details>

<details>
<summary><b>What does the session do?</b></summary>

After successful login, the server stores the user's identity in a session. The browser sends its session cookie with later requests. Protected routes use `requireLogin` to reject requests without a logged-in session.

</details>

<details>
<summary><b>How are passwords handled?</b></summary>

The registration flow hashes passwords with bcrypt. Login compares the supplied password against the stored hash. The project uses environment variables for the published copy's private database and messaging configuration.

</details>

<details>
<summary><b>How is the billing balance calculated?</b></summary>

The browser calculates the remaining amount from the total cost and amount paid. The total, paid amount and balance are saved in the billing record. For the example above, `4500 - 2000 = 2500`.

</details>

<details>
<summary><b>What is the role of MySQL?</b></summary>

MySQL stores the application's records beyond a single page or browser session. Tables separate accounts, patients, treatments, prescriptions and bills, while account IDs and patient references associate the records used by the application.

</details>

<details>
<summary><b>What would you improve next?</b></summary>

Possible extensions include appointment time slots, downloadable documents, pagination, stronger validation and deployment configuration. Describe these as future work; they are not features of the current demonstration.

</details>
